# The tap.python spike (plan 9.0) — throwaway

> **The spike's class is gone.** 9.3 built the real `tap.python` and removed `tap.python_spike.cpp`
> and its `TAP_PYTHON_SPIKE` option, so what follows is the record of 9.0: to run these patchers
> again, check out a commit before 9.3's (`f55984c`, say), where the instructions below still hold.

`docs/TAP-PYTHON-PLAN.md` item 9.0: before any of 9.1 onward is built, answer in a real Max what
the design of `tap.python` rests on. The answers, with the Max version they were verified in, are
written into the plan under 9.0; this folder is how they were found, kept so the Windows session
(and anyone checking) can repeat them. Nothing here ships, and none of it is a test suite: when
Phase 9 is built, `runtime-tests/make_patchers.py` gains the real tests (9.5) and this folder can
go.

## What is built

`-DTAP_PYTHON_SPIKE=ON` (off by default; never in a release) compiles
`source/projects/tap.python_tilde/tap.python_spike.cpp` into `tap.python~`'s binary, and its
`ext_main` registers, after min's `tap.python~`:

- **`tap.python`** — a plain SDK class (`class_new`/`class_addmethod`/`class_register`, no min, no
  Python), as D11 describes: a dumpout outlet made first and stored in the obex, with
  `object_obex_dumpout` as its `dumpout` method; value outlets (`[tap.python 3]`, default 2); an
  instance attribute `steps` and instance methods `hello`, `int`, `who`, `bang`
  (`[tap.python 1 bare]` adds none); a class attribute `level`; a class-level `anything`; and
  messages that ask Max things — `outlets n` (change the outlets between `dynlet_begin` and
  `dynlet_end`), `describe`, `fire`, `probe`, `getdump`, `attrmethod`, `thread`, `outmsg`, `outsym`.
  Every line it posts starts `spike:`.
- **`tap.python.spike.nodumpout`** — the same class without the `dumpout` method (question 3).
- **`tap.python.spike.recorder <label>`** — posts every message it receives with its label, its
  selector and each atom's type. The patchers use it instead of `[print]`, whose name Max's log
  drops and which shows no types. Like the others it exists only once the binary is loaded, so in
  a patcher it must come after a `[tap.python]` or `[tap.python~]`.

`init/tap.python.txt` (`max objectfile tap.python tap.python~;`) is real, not spike: it is how Max
finds `tap.python`, and `scripts/assemble-package.py` ships `init/`.

## The patchers

Generated by `make_spike_patchers.py` into `patchers/` (edit the generator, not the patchers). Each
runs itself on load and says what it saw in the Max console.

| Patcher | Question |
|---|---|
| `tap.python.spike-q1-mapping` | 1: only `[tap.python]`, in a **fresh** Max — found through `init/`? (Move `init/tap.python.txt` aside to see the control: `No such object`.) |
| `tap.python.spike-q1-spike-first`, `-q1-tilde-first` | 1: both objects in one patch, each created first, in a fresh Max |
| `tap.python.spike-q2-outlets` | 2: `outlet_insert_after`/`outlet_delete` against the dumpout and the cords |
| `tap.python.spike-q3-dumpout` | 3: `get<attr>` from the obex-stored dumpout, with and without the `dumpout` method |
| `tap.python.spike-q4-dispatch` | 4: what reaches a class-level `anything`; `object_getmethod()` on it and on `tap.python~` |
| `tap.python.spike-q5-threads` | 5: the thread of a `metro`-driven message: Overdrive off, on, and with Scheduler in Audio Interrupt (it starts audio for about a second, and puts both settings back as it found them) |
| `tap.python.spike-q6-strings` | 6: a string output as the message it names and as `symbol <s>`, into `route`, `sel`, `prepend` and a message box's `$1` |

Question 7 (where Max reads a vignette and a tutorial in the package's `docs/`, and whether an
`extras/` patcher is in the Extras menu) has no patcher of its own: `q7/` holds three vignettes,
three tutorials (with the tutorial's patcher) and an Extras patcher, laid out as they go into the
package. Copy `q7/docs/*` into the package's `docs/` and `q7/extras/` to its `extras/`, restart
Max, and look for "PythonTap spike vignette (…)", "PythonTap spike tutorial (…)" in the
Documentation window and "PythonTap Spike Extras" in the Extras menu. Remove them afterwards.

## On a Mac

```sh
cmake -S . -B build-spike -DTAP_PYTHON_SPIKE=ON && cmake --build build-spike
python3 runtime-tests/spike/run_spike.py        # quit Max first; about six minutes
```

`run_spike.py` uses `runtime-tests/run.py`'s harness to start and quit Max, opens each patcher in a
fresh Max (the q2–q6 patchers share one), reads Max's own log afterwards, and writes the lines of
interest to `results/macos.txt` (committed: the evidence behind the plan's answers). For q7 it
copies `q7/` into the package, waits for Max's file database, asks the database what it recorded,
and removes the copies. It turns off "Restore Windows on Launch" for the run and moves Max's
crash-recovery workspaces aside to `runtime-tests/logs/` — a window restored at launch (a help
patcher with a `tap.python~` in it) loads the binary before the patcher under test, and no Max is
then fresh — and it restores Max's preference files when it is done. The build writes the same
`externals/` folder as `build/`: rebuild `build` afterwards to put the shipping external back.

## On Windows

`run_spike_windows.ps1` is `run_spike.py`'s counterpart, without the macOS-only harness: each
patcher runs in a fresh Max of its own, started as Explorer starts it (`Max.exe "<patcher>"`)
together with a small patcher that sends `; max clean; max quit` once the patcher under test has had
its time (q7 runs until Max's file database reports its update complete). It reads Max's log
(`%APPDATA%\Cycling '74\Max 9\Logs\Max.log`), writes `results\windows.txt`, turns off Restore Windows
on Launch for the run and puts Max's preference files back afterwards. With the runtime installed
(`scripts\install-runtime.ps1`) and Max quit:

```powershell
cmake -S . -B build-spike -DTAP_PYTHON_SPIKE=ON
cmake --build build-spike --config Release
mklink /J "C:\ProgramData\Max 9\Packages\PythonTap" <this checkout>
mklink /J "C:\ProgramData\Max 9\Packages\PythonTap-spike" <this checkout>\runtime-tests\spike
powershell -ExecutionPolicy Bypass -File runtime-tests\spike\run_spike_windows.ps1
```

(`C:\ProgramData\Max 9\Packages` is Max's system-wide Packages folder on Windows. In a Parallels VM
whose Documents folder is the Mac's, the per-user one is the Mac's own `~/Documents/Max 9/Packages`,
where a junction cannot be made — and which the Windows test should not touch. To run the glue test
there, put `support\` on `PATH` first, as CI does: without it the test stops at a modal "python313.dll
was not found" dialog.)

Or by hand, with the package in a Packages folder:

1. In Max's preferences, turn off **Restore Windows on Launch** (or make sure no patcher with a
   `tap.python~` in it is open when you quit), and quit Max.
2. **Q1:** start Max and open `patchers\tap.python.spike-q1-mapping.maxpat` (File > Open). The
   console must say `spike: tap.python registered by tap.python~'s ext_main…` and then
   `spike: new tap.python…`. Quit; move `init\tap.python.txt` aside; start Max and open it again:
   `tap.python: No such object`. Put the file back. Then, each in a fresh Max,
   `…-q1-spike-first` and `…-q1-tilde-first`: both objects load, `recorder q1-spike` shows `1`
   and `0`, and `python: hello q1, from python!`.
3. **Q2–Q6:** in one Max, open `…-q2-outlets`, `…-q3-dumpout`, `…-q4-dispatch`, `…-q6-strings`
   and `…-q5-threads` in turn, a few seconds each. Save the console (or compare it line by line)
   with `results/macos.txt`. In q4, the `probe` lines will say "not equal to method_false as this
   module sees it" on Windows — expected: the module's `&method_false` is its import thunk (the
   1.0.1 lesson). What matters is "SAME AS / differs from what it answers for a name no class
   has". In q5, note the audio driver (ASIO, WASAPI, …) beside the results.
4. **Q7:** as above, if not done on the Mac.

Turn **Restore Windows on Launch** back on if it was on, and rebuild `build` for the shipping
external. Write what differs from the Mac into the plan under 9.0, with the Max version.
